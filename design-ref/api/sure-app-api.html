Sure App API v1

Everything the Sure App needs: sign-in with an iSure account, browsing and buying from SureStore with prices and stock checked live, orders, home-setup visits, TechVault warranty, repairs, and the member's points, tier and rewards from iSure. One API, one error format, JSON over HTTPS.

Base URL (Development)
https://localhost:7231/api/mobile/v1
Staging and production
Provided by the SureStore team
Auth
One bearer token for every endpoint: the token from iSure's sign-in, or the Sure App's own token
Machine-readable
/openapi/v1.json and /scalar on a Development server

Shop and loyalty systems

The app talks to one API. Behind it, every endpoint is answered by the SureStore shop system, by the iSure loyalty app, by data this API keeps itself, or by a mix. The app never calls SureStore or iSure directly. Each endpoint below carries the same labels.

  APP["Sure App (iOS / Android)"] -->|"/api/mobile/v1 · one token, one error format"| API["Sure App API (SureStoreMobileApi)"]
  API -->|"catalog, Cin7-checked price and stock, checkout, orders, stores, devices, repairs"| SS["SureStore shop system (SureStoreApi)"]
  API -->|"sign-in and PIN, profile, points, tiers, rewards, loyalty notifications, XtraGuard plans"| IS["iSure loyalty app (ISureApi)"]
  API -->|"sessions, bag, wishlist, reviews, visits, claims, addresses, preferences"| DB[("Sure App data (mobile schema)")]

SureStore shop

SureStore's shop system: products and prices, stock checked against Cin7 on product detail and checkout, quotes, orders (APP- online orders handled in SureStore Fulfillment), order tracking, stores, devices sold and repairs. Talked to with a channel key; the app never sees it.

iSure loyalty

The iSure loyalty app's API: sign-in with the iSure PIN, profile, points and club score, tiers, transfers, top-up codes, rewards, member coupons, Pay in store, loyalty notifications and XtraGuard plans. Called with the member's own iSure session, which this API keeps server-side.

Sure App data

Kept by this API: app sessions and tokens, bag, wishlist, reviews and store follows, home-setup visits, warranty claims, addresses, preferences, banners, brands, official stores and text pages.

Quick start

  1. Send the app headers on every call

    X-App-Version: 1.0.0, X-Platform: ios or android, and Accept: application/json. Below the minimum version every call except app-config answers 410 mobile.update_required.

  2. Load the app config

    GET /api/mobile/v1/app-config

    It gives the version gate, the support phone, the onboarding slides and the checkout payment options.

  3. Let the shopper browse signed out

    home, products, products/{id}, brands, vendors, stores and content work without a token.

  4. Sign in once, with iSure

    POST {iSure}/api/account/login         { "phone": "09776234118", "PIN": "••••••" }
→ { "appID": "...", "tokenResponse": { "accessToken": "...", "refreshToken": "..." } }

    Use that accessToken as the bearer on this API. Or sign in through this API's own auth/phone/check → auth/login (same phone and PIN), which returns a Sure App token. Either token works on every endpoint.

  5. Call member endpoints with the token

    GET /api/mobile/v1/loyalty/summary
Authorization: Bearer <accessToken>

    When a call answers 401 mobile.unauthenticated because the token ran out, renew it once (an iSure token with iSure's getnewtoken, a Sure App token with auth/refresh) and repeat the call.

Conventions

HeadersX-App-Version, X-Platform (ios | android), X-Device-Name on sign-in, Accept-Language (en, my reserved). Authorization: Bearer <accessToken> on member calls.
IdempotencySend Idempotency-Key: <uuid> on writes that create something or move points; endpoints marked Idempotency-Key required refuse without it (400 mobile.idempotency_key_required). A retry with the same key replays the first answer with Idempotent-Replayed: true. Same key with a different body → 422 mobile.idempotency_key_reused; still running → 409 mobile.idempotency_in_progress. Keys last 24 h per member. Generate one key per user action and reuse it for that action's retries.
Money{ "value": 1150000, "currency": "MMK" }. Never add up money in the app: every line total, fee, discount and total comes from the API. Points are integers; 1 point = 1 MMK in value.
DatesTimestamps are ISO 8601 in UTC (2026-11-03T03:49:39Z); calendar days are 2026-11-12. Show them in Myanmar time (UTC+06:30).
Lists?cursor=&limit= → { items, nextCursor }. nextCursor: null = last page. Cursors are opaque strings.
IdsProducts by SKU or VG- variant-group code; orders by number (APP-26-1193); rewards by iSure policy id; notifications i:<n> (iSure) or m:<uuid> (shop); warranty plans {source}:{serial}:{n}; repairs by ticket number.
NullsFields marked optional are left out of the JSON when empty. Treat a missing field as null.
ImagesEvery imageUrl is absolute. Product photos are cached for a day; a missing photo returns a neutral placeholder.
FreshnessProduct detail and checkout carry freshness: fresh / synced = price and stock were just checked against Cin7 through SureStore; stale / busy = Cin7 couldn't be reached and the figures are SureStore's last known; off = the store doesn't use Cin7.
ErrorsRFC 7807 Problem Details: { type, title, status, detail, code, errors[], requestId }. Switch on code, show detail (written for the shopper), put errors[] ({ field, code, message }) under the form fields. 503 mobile.upstream_unavailable means iSure or SureStore couldn't be reached: offer Retry. Quote requestId in support tickets.

Sign-in and tokens

The member's password is their iSure PIN, shared with the iSure app. Any existing PIN signs in; the rules (at least 8 characters, a letter and a number) apply only when a password is created or changed.

sequenceDiagram
  participant App
  participant API as Sure App API
  App->>API: POST auth/phone/check {phone}
  alt status = password
    API-->>App: password
    App->>API: POST auth/login {phone, password}
  else status = otp_sent (new member or no password yet)
    API-->>App: otp_sent + purpose
    App->>API: POST auth/otp/verify {phone, purpose, code}
    API-->>App: ticket (10 min)
    App->>API: POST auth/password {ticket, password, confirm}
  end
  API-->>App: accessToken (15 min) + refreshToken (30 days)
  Note over App,API: Forgot password: POST auth/otp {purpose: reset} → otp/verify → auth/password
  App->>API: member calls with Authorization: Bearer accessToken
  App->>API: POST auth/refresh {refreshToken} when a call answers 401
  API-->>App: new accessToken + new refreshToken (store both)

One sign-in place: the iSure token works everywhere

The member signs in once, with iSure. The token iSure gives back (POST {iSure}/api/account/login → tokenResponse.accessToken) is accepted as Authorization: Bearer on every endpoint of this API: SureStore shop iSure loyalty Sure App data.

  • The API checks each new iSure token with iSure once and remembers the answer until the token expires. iSure's tokens last 5 minutes.
  • When a call answers 401 mobile.unauthenticated, renew the token with iSure (GET {iSure}/api/account/getnewtoken?refreshToken=…) and repeat the call.
  • Behind the token, the API calls iSure with that same token and SureStore with its own channel key plus the member's phone. The app never calls SureStore directly; SureStore doesn't accept member tokens.
  • Signing out can't cancel an iSure token on the server; it ends when it expires.

The API's own sign-in endpoints below (auth/login and the rest) still work and give a Sure App token (15 minutes, with a rotating 30-day refresh token). Use either one; both open the same member's data.

Store the refresh token safely

Keep it in the Keychain / Keystore. App Lock (Face ID, fingerprint) unlocks the stored refresh token and calls auth/refresh.

It rotates every time

Each refresh returns a new refresh token. Presenting an old one ends that session, so refresh from one place in the app and save the new pair before anything else.

Sessions end elsewhere

Up to 5 installs stay signed in per member; the oldest is signed out. A signed-out install gets 401 mobile.session_ended: go to sign-in.

Checkout flow

The bag shows last-known prices. Checkout asks SureStore for a quote (price and stock refreshed from Cin7) and places the order against the total the member saw. Payment in this release is cash on delivery or pay at pickup.

flowchart TD
  A[POST cart/items] --> B[POST checkout/quote]
  B -->|member changes mode, shipping, address, store or home setup| B
  B -->|canPlace = false| P[Show problems; fix the bag]
  B -->|canPlace = true| C["POST orders + expectedTotal + Idempotency-Key"]
  C -->|OrderPlacedDto| D[Confirmation sheet → Track order]
  C -->|409 channel.price_changed or mobile.out_of_stock| Q[Show problem.quote, ask again]
  Q --> C
  C -->|timeout| R[Retry with the same Idempotency-Key]
  R --> C

Home setup at checkout

For delivery, homeSetupDays lists open windows. Send homeSetup: { date, slot } in the quote and in orders; the visit is booked with the order.

Points at checkout

points shows the balance and an estimate of points earned. Paying with points isn't in this release (canRedeem: false).
